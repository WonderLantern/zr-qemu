# WonderLantern ZR QEMU


[Portable ZR recording qualification / 公开包录制验收](docs/recording-qualification221.json)

[English / 完整构建启动命令](README.md) · [当前证据、实现与限制](docs/shared221.md) · [本地输入要求](docs/zr-inputs.md)

QEMU10.2.4上的ZR C1.11研究模拟器，复用Z9的共享EXPEED7设备。菜单、
拍摄HUD、快门控制、元数据和文件写入执行用户自己的原固件。项目仅作
研究学习，不代表尼康/RED官方产品；尊重其权益，不公开其私有代码。
源码包不包含固件、ROM/校准/字体/图标数据、厂商SDK、照片或录像。

## 本地完整录像验收

|格式|第一段|第二段|
|---|---|---|
|4K H.265 Main10，29.97fps|909帧，30.3303秒|909帧，30.3303秒|
|6K R3D NE，59.94fps|1803帧，30.08005秒|1806帧，30.13010秒|

同一shared221本地构建中，两种格式均通过两次开始/停止、原固件实际
写卡、完整独立文件核验及两次菜单返回新取景。1818帧Main10全部解码；
3609个真实RAW包逐字节核验，代理视频3609帧全部解码。两段R3D的首/
中/尾共六张真实画面通过独立RED内容检查。静态CMOS供图产生相同RAW
码流，重复帧只有在完整字节相同后才复用独立解码结果，不能仅比较CRC。
公开启动器的整机回归与本地参考构建分别记录，构建或START回调不等于
录像通过。

**这仍是功能后端。** HE为原创正向编码及公开LibRaw逆变换，HEVC/AVC
使用x265/x264，ISP/JPEG使用功能实现；原厂ISP/DSP/H265/RAW/JPEG算法
均未验收。R3D暗部/色彩仍未校准；Main10确实为10bit语法，但当前源的
有效精度来自8bit功能图像链路。不能宣传为物理传感器有效精度或原厂效果。

## 构建和运行

Linux、Python3.12+、C/C++17，使用Linux构建目录。Windows研究主机明确
选择ubuntu-noble-nikon，课程用ubuntu-noble不参与。构建步骤、依赖、
命令见英文README。用户提供匹配MAIN和捕获资源：**MAIN单独目前不够**，
具体文件指纹见输入文档；缺失时明确报错，不下载或补入私有内容。

`tools/make_cmos.py --image`可把用户自己的图生成RGGB/u16；14bit输入
约定不是已测量的CMOS总线协议。`tools/run_zr.py`选择preview/photo/
main10/r3d，每次使用新的输出目录。默认横屏、明确记录的英文缓存偏好。
ISO、快门、原生文字和图标由固件绘制；本版未提供ZR网页控制器。

main10/r3d配方各执行两段30秒及两次菜单返回。视频半按对焦，持续半按
加全按开始，随后全按停止。`video-recording-live.json`提供实时编码
计数；旧阶段快照与尚未刷卡的编码环形缓存不能作为卡死证据。

普通稀疏卡为默认方案，两段R3D约28GB，建议至少留40GiB含证据空间。
可选`--deduplicated-card`在Linux FUSE文件上无损共享4KiB页，需要安装
libfuse2及Python fusepy，保留初始卡/SQLite数据库/服务回执以便重挂。
它只是宿主存储优化，保留固件写出的全部原始字节，不接触物理相机卡。

运行目录可能含私有数据，只能留本地。`--audit`目前只审计照片；录像
须从result.json中的真实虚拟卡导出并做完整独立解码。R3D可用用户自己
已授权安装的RED/Resolve等兼容解码器，本仓库不分发其代码或SDK。

## 保留的工作

ZR C1.10录像、Z9视频、原厂算法、色彩校准、完整长连拍及拍后恢复、
SD/CFE物理身份、预拍摄与长期稳定性仍未完成，不能用C1.11的数据代证。
历史shared146照片证据保留原构建范围。XM6资料存在但版本对应未证明；
NeuPro详细文档缺失，本地神经网络复现inconclusive。Z7及原始输入不改。
